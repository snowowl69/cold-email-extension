Technical report

Placement Email Bot

A Manifest V3 Chrome extension that prepares contacts and email templates in a popup, persists campaign state locally, and drives Gmail through a content script that opens, fills, and sends messages sequentially.

Architecture Popup + service worker + Gmail content script
Execution model Client-side automation inside Gmail
State storage chrome.storage.local for contacts, templates, logs
Primary risk Gmail selector drift and long-running worker behavior
Source: chrome-extension workspace Report format: HTML Print-ready: yes
01 / overview

What this extension does

The project is a Gmail-native outreach tool. The popup is the operator console, the background worker is a relay and persistence layer, and the content script is the executor that manipulates Gmail's compose UI. No server is involved; the extension runs entirely in the browser.

Control plane

  • popup.html renders the operator dashboard.
  • popup.js parses CSV, edits templates, stores state, and starts/stops runs.
  • popup.css provides the polished visual system.

Execution plane

  • content.js automates Gmail compose and send actions.
  • background.js keeps state synchronized and relays stop events.
  • manifest.json wires permissions, host access, popup, and service worker.
The core design is sound: the UI prepares the payload, the background worker keeps the session state available, and the Gmail content script performs the actual send loop.

03 / flows

How the send cycle works

The content script performs a deterministic sequence: open compose, fill fields, send, wait, then repeat until the send limit or stop flag is reached.

Send sequence
sequenceDiagram participant User participant Popup participant Content as content.js participant Gmail participant Bg as background.js participant Store as chrome.storage.local User->>Popup: Upload contacts and set template Popup->>Store: Persist contacts, template, settings User->>Popup: Start sending Popup->>Content: start_sending payload loop For each recipient Content->>Gmail: Open compose window Content->>Gmail: Fill To, CC, BCC, Subject, Body Content->>Gmail: Click Send Content->>Bg: progress_update Bg->>Store: Persist updated sendingState Bg-->>Popup: progress_update end Content->>Bg: sending_complete Bg->>Store: Mark session complete Bg-->>Popup: sending_complete

Per-recipient behavior

  • Generate subject and body by replacing placeholders such as {name}, {company}, and {position}.
  • Open Gmail compose and wait for the UI to stabilize before writing values.
  • Click Send and then wait briefly so Gmail can show confirmation feedback.
  • Log each success or failure in memory and mirrored storage.

Flow controls

  • The loop stops when the send limit is reached.
  • A stop request sets shouldStop and exits after the current attempt.
  • Each iteration waits the configured delay before the next email.

06 / implementation

Component-level behavior

The code is simple, but each component has a distinct responsibility boundary.

Popup layer

  • Accepts CSV input and uses a hand-written parser that supports quoted fields and multiline values.
  • Offers placeholder chips that insert tokens into subject/body fields.
  • Renders a live preview from the first contact or a synthetic fallback contact.
  • Persists template, settings, and contacts to local storage.

Gmail layer

  • Uses several fallback selectors for compose, To, CC, BCC, Subject, Body, Send, and discard actions.
  • Simulates input events so Gmail's own handlers can recognize changes.
  • Sends one message at a time and waits between recipients according to the configured delay.

Background layer

  • Acts as a bridge between runtime events and persistent storage.
  • Stores the latest progress and final log so the popup can recover after closure.
  • Relays stop commands to every open Gmail tab.

Data model

  • Contacts are treated as dictionaries, so any CSV header can become a placeholder.
  • Email templates are plain strings with token replacement.
  • Logs record timestamped info, success, and error entries.
07 / assessment

Strengths, risks, and gaps

The project is functional and readable, but it also has a few risks that are worth documenting because they shape how reliable the extension can be over time.

Strengths

  • All logic runs locally in the browser, so there is no backend dependency.
  • State persistence makes the session recoverable after popup closure.
  • Multiple selector fallbacks improve resilience against minor Gmail UI changes.
  • The code is modular enough to explain and maintain without external libraries.

Risks and gaps

  • High: Gmail DOM selectors can break when Google changes the UI.
  • High: The service worker keepalive listener exists, but no code currently opens the port, so long sessions may still rely on Chrome's worker lifetime behavior.
  • Medium: The popup accepts .xlsx files but explicitly warns that parsing is CSV-only.
  • Medium: There is no attachment handling, which the UI already acknowledges.
  • Medium: The send loop is sequential by design, so throughput is intentionally limited.
The biggest technical dependency is not the extension framework itself; it is Gmail's current DOM and accessibility structure.
08 / roadmap

Recommended improvements

If this extension is meant to become more production-ready, the following additions would materially improve reliability and clarity.

Reliability

  • Add a real keepalive port connection from the content script if long sessions must survive worker suspension.
  • Normalize and validate CSV columns before send time, with clear user-facing diagnostics.
  • Separate Gmail selectors into a dedicated helper file for easier maintenance.

Usability

  • Add explicit import/export for campaign templates and logs.
  • Provide a dry-run or preview-only mode to verify personalization before sending.
  • Expand the report to include screenshots if the extension evolves into a deliverable product.

Conclusion

Bottom line

The extension is a focused browser-native campaign tool with a clear three-layer split: user preparation in the popup, orchestration in the background worker, and execution in the Gmail content script. Its architecture is understandable and practical, but its long-term reliability depends on Gmail selector maintenance and on ensuring the service worker remains available for long send sessions.
